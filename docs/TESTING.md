Every check this project runs, and what each test file is actually holding
in place. Most rows name a defect that reached a document before the test
existed — that is the point of writing them down rather than counting them.

The seven between `check:docs` and `check:sidecar` need nothing but the source
tree and run in under a second each. They exist because every one of them covers
a fault that is **silent**: a migration checked out with the wrong line endings
refuses to open a database the other spelling created; a font face whose file is
missing falls back and says nothing; an `http://` in an exported KMZ is a
cleartext request from the client's machine when they open it; an icon path
that drifted renders as a default pin; and a card heading with no icon renders,
type-checks and reads fine on its own, and only looks wrong beside the twelve
that have one — a comparison no reviewer makes either, because they are five
hundred lines apart in the same file.

The last two need a built application, like `check:sidecar`.

`check:sidecar` is the one to run between `npm run tauri build` and compiling
the installer. See below for the engine that would not start.

### Nothing in the report may be drawn off the page

`npm run check:margins` reads the `re` (rectangle) operators out of every pinned
baseline PDF and measures each against its own page box, so an overflowing table
is provable from the file rather than argued about from a screenshot. Currently
**52 pages across two documents**.

"Every pinned baseline" is recent and fixed two faults at once. The check defaulted
to the single `scripts/baseline-report.pdf`, which the export harness stopped
writing when baselines became one-per-shape --- so it went on *passing* while
measuring a frozen file no build could change, which from the outside looks exactly
like a real pass. And the wireless report was the only shape it had ever measured:
the LAN document's subnet coverage and host tables, 16 pages of them, had nothing
looking at their column widths. Both documents measure clean. A pin with no
recorded PDF exits 2 rather than passing, and a document with no content streams
is a failure rather than the quietest pass available.

It exists because the WiFi telemetry table was given eleven columns summing to
202 mm on a 178 mm content column and nothing objected. The table was drawn to
**216.1 mm on a 210 mm sheet**: its last column - the severity verdict - began at
198.1 mm and printed entirely off the paper, on eleven pages, for as long as that
table existed. A column width is a number somebody types, and it was checkable
all along.

The check was verified in both directions: it fails on the pre-fix document
naming 372 items across 11 pages, and passes on the current ones. Both new refusals
were verified the same way --- an index naming an unrecorded pin exits 2, and a
two-line PDF with no content streams fails rather than passing.

What it cannot see is a line of text that *starts* inside the margin and runs
past it — jsPDF has already wrapped by then and the file records no width.
`layout.paragraph` wrapping to the content column is the control that covers
that, which is why page geometry is derived in one place
(`src/lib/report/geometry.ts`) rather than typed out per section. It had been
typed out per section: `14`, `182`, `196`, `287`, `292` and `25` appeared by hand
across four files with nothing connecting them.

Note the WiFi telemetry annexe is **landscape**. Eleven columns of measurements
do not fit a portrait page, and shrinking them to fit would have cost the BSSID
column, which already could not hold a 17-character MAC at 6.5 pt. The header and
footer read the page they are on for the same reason — the previous hardcoded
footer would have landed 77 mm below a landscape sheet.

### The bundled sidecar must be the sidecar that was built

`npm run check:sidecar` compares `src-tauri/binaries/ewac-engine/_internal`
against `src-tauri/target/release/_internal` file by file **and byte by byte**,
and fails on a file present in the bundle that the sidecar did not build, a file
the sidecar built that did not reach the bundle, or a file that is in both under
the same name with different contents.

That last one was added after the check spent some time reporting a stale copy as
an exact match. It diffed the two sets of *relative paths* and printed "matches
the sidecar exactly" --- names, not bytes, and a stale copy has exactly the same
names as a fresh one, which is the only way for it to be stale. Rebuilding the
sidecar without rebuilding the app produces precisely that state, because Tauri
does not re-copy when its build script is fingerprint-clean. The first run after
the change found `base_library.zip` differing at identical size and the staging
executable **1,254 bytes smaller than the one just built** --- which was the
pre-fix engine, driving both release harnesses while a passing check said
otherwise. The executable is compared too; it had been outside the comparison
entirely, despite being the one file whose staleness changes behaviour on its
own.

`tauri build` copies into that directory **without clearing it**, so anything a
previous sidecar build put there survives every later build and ships. One
rebuild left 244 orphans behind. The fatal one was `_internal/yaml/` holding a
single file --- `_yaml.cp313-win_amd64.pyd`, PyYAML's optional C accelerator ---
and no `__init__.py`, left over from before PyYAML was removed from the
virtualenv.

A directory without an `__init__.py` is a **namespace package**, so
`import yaml` succeeded and returned an empty module. paramiko guards that
import with `except ImportError`; the guard never fired, and the engine died at
startup on `AttributeError: module 'yaml' has no attribute 'error'`. The orphan
converted an absence the code handled into a crash it could not.

Nothing else can see this. The engine suite passes, because it runs against
source in a virtualenv where a missing dependency is a clean `ImportError` and a
half-collected package cannot exist. So the check does two things: it **starts
the frozen engine** and requires its `ready` event --- the only place in this
project that runs the frozen engine at all --- and it compares the two trees,
naming an entirely-orphaned package explicitly, because that is the shape that
shadows rather than merely wasting space.

**What that directory governs.** It is the staging copy used when
`target/release/lockon-ewac.exe` is run directly, which is what
`test:csp:release` and `test:export:release` do. Tauri's MSI and NSIS bundles
read the sidecar from `binaries/ewac-engine/` instead, and `lockon-ewac.iss` now
does the same, so neither depends on it.

**Deleting it is not the fix.** Tauri does not re-copy resources when its build
script is fingerprint-clean, so a rebuild after deleting them leaves
`target/release` with no engine at all. Restore it by copying:

```bash
cp -r src-tauri/binaries/ewac-engine/_internal src-tauri/target/release/_internal
cp src-tauri/binaries/ewac-engine/ewac-engine-x86_64-pc-windows-msvc.exe src-tauri/target/release/ewac-engine.exe
```

### One PDF baseline per document shape

`scripts/baselines/` holds one PDF per pinned archive and an index of the pins,
and a comparison run exports every one of them in a single app launch.

**Pinned, because "the first archived report" is only stable while the archive
is.** Running a scan put a newer survey on top, the next run exported a different
document, and it reported 77 differences that had nothing to do with the code. A
regression net that cannot distinguish "the build changed the document" from "a
different document" is worse than none, because every real difference after that
gets read as noise. A missing pin fails loudly rather than falling back.

**More than one, because a wireless survey and a LAN sweep draw different halves
of the document.** The survey figure, the rogue assessment, WPS exposure and
position quality render only for the first; the subnet sweep coverage and the host
tables only for the second. A single pinned archive therefore checked about half
the builder, and which half depended on which archive was pinned — eleven PDF
sections were extracted against a pinned `INTRUSION` report, so six of those moves
had `tsc` behind them and nothing else. Measured once both existed: the wireless
document holds **1,455 strings the LAN one does not**.

The launch and the sidecar wait are the expensive parts, not the export, so the
second shape costs about a minute rather than doubling the run. A pin with no
recorded baseline is **not** a pass — it reports `NO BASELINE RECORDED` and exits
3, the same code used for "nothing to compare against", because a release script
reading exit 0 for a comparison that never happened is the worst outcome available
here.

    node scripts/export-smoke-test.mjs                                    # compare every pin
    node scripts/export-smoke-test.mjs --write-baseline                   # re-record them all
    node scripts/export-smoke-test.mjs --write-baseline --report <id>     # pin another

`--report` requires `--write-baseline`: on its own it meant "compare against a
different survey", which is the outcome the pin exists to prevent.

### The CSP has two policies, and only one of them ships

Tauri injects **`app.security.devCsp`** under `tauri dev` and **`app.security.csp`**
in a build. For a long time `devCsp` was unset, which does not mean "same policy"
— it means *no policy at all* in development. `npm run test:csp` runs under
`tauri dev`, so every PASS it printed said nothing whatsoever about the policy
that ships.

Two real defects hid behind that, both invisible on any developer machine and
present in every installed copy:

- **The basemap.** `csp` allowed `https://basemaps.cartocdn.com`, but the style
  served from there loads its tiles, glyphs and sprite from
  `tiles.basemaps.cartocdn.com`, and CSP host matching is exact without a
  wildcard. The style document fetched; everything it referenced was blocked; the
  map fell back to the offline grid. Fixed with `https://*.basemaps.cartocdn.com`.
- **The webfonts.** `index.html` loaded the Google Fonts stylesheet with
  `media="print"` so it would not block the first paint, and flipped it to `all`
  with an `onload` attribute. An inline event handler is governed by
  `script-src-attr`, which falls back to `script-src`, which allows nothing
  inline — so the flip never ran, the sheet stayed print-only, and the fonts never
  applied. The app rendered on the fallback stack with nothing reporting a
  problem. The flip now happens in `src/main.tsx`, which needs no inline script.

Three guards exist now, and they are layered because no single one is enough:

1. **`devCsp` is set** to the production policy plus the dev server's own
   origins, so a dev run exercises something close to what ships.
2. **`checkPolicyDrift()`** runs before the app launches and refuses to continue
   if `devCsp` is missing, or allows any source `csp` does not. It exits 2 and
   names the offending directive and source. Verified against all three states,
   including the one that shipped the basemap bug.
3. **`npm run test:csp:release`** drives `src-tauri/target/release/lockon-ewac.exe`
   instead of the dev server. This is the only check that exercises the real
   policy, and it is the one that found the webfont bug.

The dev policy legitimately needs `'unsafe-inline'` for scripts — Vite injects
them — so inline-script problems *cannot* be caught by `test:csp` by
construction. That is precisely what the release mode is for. **Check a webview
policy against the built binary, never the dev server.**

A note on the harness itself, because it cost a wasted quarter of an hour:
`launchApp()` spawns `npm` through a shell because npm is a `.cmd`, but doing the
same to the built `.exe` broke it — the relative path uses forward slashes, `cmd`
did not launch it, and the harness waited out its entire fifteen-minute attach
timeout with nothing to attach to. It looked exactly like WebView2 refusing the
debugging port. The release binary is now spawned directly, with an absolute
path and no shell, and attaches in about a second.

### The PDF regression net

`buildAndSavePDF` is the one product path `npm test` cannot reach: `tsc` passes
over it, every unit suite stops short of it, and the report is what this project
exists to produce. A rewrite of `ReportsPage.tsx` once landed with ~2,700
insertions while the newest PDF the app had actually produced was older than the
code that would produce the next one.

`npm run test:export` closes that. It launches the real app, waits for
**"Engine: ONLINE"** (the sidecar takes 7-23 seconds to start, and exporting
early produces a document that correctly reports the engine as unreachable --- one
page shorter, which reads as a code change when the invariant was working),
selects the first archived report via `data-report-row`, exports a PDF, and
compares it against a baseline through `scripts/pdfdiff.mjs`.

A byte or hash comparison would be useless: the document carries its own creation
date and two SHA-256 stamps, so two runs of identical code differ in every one of
those places. `pdfdiff.mjs` extracts the literal strings from each content
stream, blanks the values expected to change (digests, dates, times, the CVE
vintage), and reports the first difference per stream.

**Validate the comparator before trusting an IDENTICAL from it.**
`npm run test:pdfdiff` does that: it compares a file with itself, requires
IDENTICAL, then flips one character in one string and requires that to be caught.
A diff tool that always says IDENTICAL is worse than none, because it turns an
unchecked change into a checked one in the reader's mind.

It reports up to eight differences **per stream** and then counts the rest. It
used to stop at the first, which was worse than it sounds: refreshing the CVE data
legitimately changed one line of the method appendix, the tool reported that one
line, and adopting the result as a new baseline would have accepted whatever else
in that stream had changed unseen. In the event it was six further lines of the
same re-wrapped paragraph and nothing more --- but a review has to be able to see
what it is approving.

One limit is inherent: jsPDF wraps paragraphs before any normalisation runs, so a
value that gains a digit --- the CVE age going from 9 to 10 days --- re-wraps its
callout and every line after it is reported as changed. Normalisation removes the
common case; when it happens, re-baseline.

**A version bump invalidates the baseline, and that is correct.** The report
prints the app version and the engine identity (`<version> - <git describe> -
built <iso>`) in its provenance, because a severity traced to a rule set is only
auditable if the software that applied it can be named. So bumping the version,
or rebuilding the sidecar, legitimately changes the document: expect a diff,
check that it is only those lines, then re-run with `--write-baseline`. A shorter
stamp also re-wraps the method appendix and can push a table row onto the next
page, which looks alarming and is not — the rows themselves are unchanged.

Two limits, both deliberate. The baselines (`scripts/baselines/`) are **not
tracked**, and the reason is not their size: the two of them come to 2.3 MB, not
the ~17 MB this paragraph claimed for the single one it replaced. The reason is
that a baseline *is* survey data. It is the document produced from one archived
scan on one machine, it changes whenever the report legitimately changes, and
committing it would be committing somebody's radio measurements of somebody's
street to the repository. So the net catches a regression *between runs on one
machine*, which is what a refactor needs, and a fresh clone records its own
baselines on the first run rather than comparing against someone else's data.

And an empty report archive is reported as a **failure to test**, not as a pass
--- there is nothing to export, and a harness that passes on no data is the
failure mode this whole file exists to avoid.

`scripts/cdp.mjs` holds the Chrome DevTools Protocol plumbing both app harnesses
share --- attaching past WebView2's `about:blank` target, refusing to start when
an instance is already running without a debugging port, and polling in short
evaluates rather than one long one. It is shared so a fix to one harness cannot
leave the other with the bug.

`npm test` runs, in order: `localization` (41), `ipc` (12), `vault` (24),
`numbers` (11), `risk` (106), `csv` (19), `db` (123), `archive` (73),
`assemble` (25), `severity` (15), `signal` (9), `router` (16), `mission` (17),
`stores` (25), `csp-reporter` (13), `kmz` (12), `basemap` (14), `cidr` (9). Each is also runnable on its own as
`npm run test:<name>`.

`npm run check:severity-css` is kept out of `npm test` because it needs a build:
it reads the shipped stylesheet and fails if a class named in `severityStyle.ts`
or `signalStyle.ts` has no rule. Tailwind finds classes by scanning source for
complete strings, so a class assembled at run time renders with **no colour at
all** — which reads as a rendering glitch rather than as a severity. That
shipped once, for MEDIUM, and `tsc`, the unit tests and the CSP smoke test all
passed while it was broken.
The suite needs no third-party packages, so it runs on a machine that has not
installed the engine's requirements. Individual files also run standalone and
the suite is pytest-compatible (`python -m pytest engine/tests`).

`npm run check:docs` reads the README and all seven files under `docs/` and fails on a claim the repository does not support: a test file that does not exist, a suite count that has drifted, an `npm run` command that is gone, a path in the project tree that was deleted, or a deleted identifier still described as live code. Three more checks were added after the split, because splitting one document into eight created a class of rot the original five could not see. **Links and anchors**: every markdown link to another document, and every heading fragment after its `#`, must resolve — a link to a reworded heading silently lands the reader at the top of the right file and looks like it worked. **Backticked paths**: any backticked string shaped like a source path must name a real file, which caught nine paths written without their `engine/` or `src/` prefix in a document that spells the prefix out elsewhere. **Backticked identifiers**: a name presented as code must appear in some source file — this one found four engine events that were never emitted, including a `passive_probe` whose 802.11 work actually lives in another module under another name, and a wrong event name fails as silence rather than as an error. It checks only what can be checked mechanically — prose has to be read — but those are exactly the claims that rot silently, and a stale line in a README reads the same as a true one. Every one of those categories had rotted at least once before this existed.

`npm run test:db` is the one suite with an environment requirement: it runs the
database modules against **real SQLite** via Node's built-in `node:sqlite`, so it
needs Node 22 or later. It applies the project's own migration files to an
in-memory database, which means the schema under test is the schema that ships —
and it is the only check that would catch a new migration written against a
table that does not exist. Two things it deliberately cannot test, because a
single connection cannot: anything that depends on which connection in a pool
served a statement (`PRAGMA secure_delete` is the live example), and real WAL
behaviour.

## The installer's runtime paths are tested by hand, and are not tested yet

Everything in `installer/lockon-ewac.iss` outside `[Code]` is checked by
compiling it. The `[Code]` procedures are not: they run only during a real
install, several need elevation, and two of them exist precisely to handle
situations a normal install never reaches. Nothing below has been executed on a
build of v1.0.0 --- that is the honest state, recorded here rather than left as
an assumption, because every one of these paths is a thing that runs when
something has already gone slightly wrong.

Run these from an elevated prompt, against `dist-installer\lockon-ewac-setup.exe`.

| # | What to run | What must happen | Which code it covers |
|---|---|---|---|
| 1 | Launch the app, leave it running, then run setup and install over it | Setup does not fail on a locked file. The running window closes; no `lockon-ewac.exe` or `ewac-engine.exe` survives into the copy step | `StopLockon()` via `PrepareToInstall` |
| 2 | Same as 1, but close the window first and leave only the engine running (kill the window in Task Manager) | The orphaned `ewac-engine.exe` is still killed | `StopLockon()` second `taskkill` |
| 3 | `lockon-ewac-setup.exe /VERYSILENT /SUPPRESSMSGBOXES` | Installs with no window and **no prompt of any kind**. A prompt here hangs an unattended deployment forever | `WizardSilent()` guard in `WebView2Confirmed()` |

Test 6 is the one most worth doing. `runasoriginaluser` is a single flag whose
absence produces an application that works perfectly in the wizard and then
writes its database into the elevated account's profile, so the operator's own
archive appears empty and nothing reports an error.

## What each component suite holds in place

The node suites below drive pure modules, stores and real SQLite. These run under
jsdom against the real components, with only the Tauri boundary and **MapLibre**
stubbed — WebGL is the other thing a browser provides and jsdom does not, and
until the stub existed every page holding a map threw on construction. The stub
records calls and draws nothing, so these prove what a surface *says*, never where
it appears.

| Suite | What it holds |
|---|---|
| `tests/components/mapPopups.test.tsx` (9) | What the live map tells an operator about a mark. Six popup builders had **no assertion between them** — the only mention of `setHTML` under `tests/` was a sentence in a comment. A reading that does not exist is `n/r` and never a blank before " dBm"; a position with no radius says so; an ambiguous one states how far apart the candidates are; an SSID cannot close a tag; an unresolved access point is not plotted as a position; the dot carries the rule set's verdict; `0, 0` is an absent column. |
| `tests/components/basemapFallback.test.tsx` (8) | The four paths into a degraded basemap, with a fake clock: no network at start, a style-level failure, a source-level failure with a 1.5 s grace, and an 8 s watchdog for a request that hangs instead of failing. The two easiest to get wrong in opposite directions are both pinned — one bad tile must **not** drop a working basemap, and a style that will never load must **not** be given a grace period. The property asserted most deliberately is the banner's second line: a degraded basemap is a broken picture, not a broken scan. |

The scope, evil-twin and localization tests matter most. The first is the
difference between a tool that stays inside its authorization and one that does
not. The second is the difference between a report that is believed and one that
makes a false accusation. The third exists because reading the estimator code
did not reveal that the weighted centroid could never leave the road or that GPR

before shipping a build.
