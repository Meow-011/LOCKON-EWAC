Symptoms, what causes them, and what to do. Some of these are limits of the
hardware or the platform rather than bugs, and they are listed as such.

## Network scanning

| Symptom | Cause | Solution |
|---|---|---|
| **0 Nodes found** on Wi-Fi subnet | **AP Isolation** is enabled on the router/AP (common in public networks: hospitals, universities, hotels) | Use a private network or connect via Ethernet. This is a network restriction, not a bug. |
| **Ghost hosts** (many "Unknown Host" with HTTP/HTTPS only) | Windows ICS/NAT (Mobile Hotspot) responds to port probes on behalf of non-existent hosts | ARP pre-filter now handles this automatically. If still occurs, use `QUICK` scan mode instead of `DEEP`. |
| **MAC shows but Vendor is "Unknown"** | The OUI (first 3 bytes of the MAC) is not in Scapy's `manufdb`, or the MAC is randomised | Randomised MACs are reported as `Randomized (Local)` rather than `Unknown`. A genuine `Unknown` means the OUI is absent from `manufdb`; updating Scapy updates the database. |
| **OS shows "Unknown"** | Host didn't respond to TTL probes or has a firewall blocking ICMP | Expected for hardened hosts. The scanner still reports open ports accurately. |

## Engagement scope

| Symptom | Cause | Solution |
|---|---|---|
| **Every offensive button does nothing / "OUT OF SCOPE" toast** | No active engagement scope, so the engine is denying by default | Define and activate one in **Settings → Engagement Scope**. This is the intended behaviour, not a bug. |
| **Scope saved but modules still blocked** | The scope reached the database but not the engine | Settings shows the database-side config and the engine-side gate side by side. Use **RESYNC ENGINE**; a mismatch banner appears when the two disagree. |
| **Everything blocked after a reconnect** | The engine restarted and lost its copy of the scope | The app re-pushes the scope on `ready`/`reconnected` automatically. If you see the "no active engagement scope" warning, re-activate it. |
| **A `/16` sweep is refused although a `/24` inside it is allowlisted** | Subnets must be a subset of an allowlisted range, not merely overlap one | Allowlist the range you actually intend to sweep. |

## Field operation

| Symptom | Cause | Solution |
|---|---|---|
| **"LOCKON EWAC could not start" — "migration N was previously applied but has been modified"** | The build's migration file does not hash to what was recorded when it was applied to this `ewac.db` | Two different causes, and the number tells you which. **A low number on a file nobody edited is almost always line endings.** `lib.rs` embeds migrations with `include_str!`, sqlx hashes that text, and with `core.autocrlf=true` git checks `*.sql` out as CRLF while storing LF — so one commit produced two checksums depending on who built it. Fixed in v1.0.0 by `.gitattributes` pinning `*.sql` to LF, with `npm run check:migrations` enforcing it. **A number at 8 or above may be a different migration entirely**: migrations 8 and 9 were once `raw_gps` and `bluetooth_schema` and are now `create_integrity_and_scope` and `create_findings_and_evidence`. sqlx identifies a migration by its number, so no checksum repair reconciles that. Read what your database actually recorded before deciding — see below. |
| **You need to know which of those two it is** | `_sqlx_migrations` records a `description` per version, which names the migration that actually ran | Open `%APPDATA%\com.lockon.ewac\ewac.db` read-only and run `SELECT version, description, installed_on FROM _sqlx_migrations ORDER BY version;`. If every description matches this build's (`src-tauri/src/lib.rs` lists them), the content is the same and the difference is bytes — line endings. If a description names a migration this build does not have, the database is on an older schema line. |
| **Your database is on the older schema line and you do not want to lose the survey** | The two schemas diverged at migration 8; the file cannot be migrated forward in place | Do **not** delete it. Copy it somewhere first, move `ewac.db` aside, start the app so it creates a fresh one, then `node scripts/migrate-legacy-db.mjs <old.db> <new.db>` for a dry run and `--apply` to copy. It carries only columns both schemas share, leaves newly added columns at their defaults rather than inventing values, and names every column it has to drop. On the database this was written for it carried 427,288 rows across nine tables and lost three columns. |
| **The offline map is still a flat grid although an archive is installed** | The file is there and something about it was refused | Open **Settings → Offline Basemap**: it shows the exact path, whether the file was readable, and the zoom range and bounds it reports. The application also says which of the three it was, in the console — `no archive at <path>`, `the host could not be asked`, or `present but its header did not parse`. The last means the file is not a PMTiles v3 archive or was copied incompletely; re-copy it and press **Re-check**. An archive whose header will not parse is deliberately treated as absent, because registering the protocol and then failing every tile is worse than drawing the grid. |
| **The offline map draws, but an area of it has no place names** | Either the archive does not cover it, or the labels are in a script whose glyphs are not carried | Settings prints the bounds the archive reports — outside them the map is plain background, which is the edge of your data rather than a failure. Inside them, Latin, Latin Extended, Thai and Devanagari are carried in the application; a label in Cyrillic, Arabic or CJK is dropped by MapLibre with nothing shown. Adding a script is one line in `scripts/fetch-basemap-glyphs.mjs` and a re-run of `npm run basemap:glyphs`. |
| **An exported map opens with plain default pins** | The KMZ names an icon path the archive does not carry | `npm run check:kmz` compares the three places those names live — the `<href>` in the exporter, the entry packed into the archive, and the file on disk — and names whichever drifted. The icons are inside the file on purpose: as URLs they were fetched from Google over plain HTTP, so a client opening the assessment sent a cleartext request at that moment. |
| **"BASEMAP DEGRADED" banner, plain dark map** | No network, or the tile CDN is unreachable | Expected *when offline*. Scanning, GPS logging and recording are unaffected and your markers and track are still shown. Hit RETRY when you have a connection. |
| **"BASEMAP DEGRADED" on a machine that is definitely online** | A Content-Security-Policy host that does not cover the CDN's subdomains | This was a real bug up to v0.1.0: `csp` allowed `basemaps.cartocdn.com`, but the style served from there loads its tiles, glyphs and sprite from `tiles.basemaps.cartocdn.com`, and CSP host matching is exact without a wildcard. Fixed in v1.0.0. If it returns after a CDN change, run `npm run test:csp:release` — it names the blocked directive and origin. |
| **Interface renders in the wrong font** | Up to v1.0.0 the fonts came from Google at startup and could fail to apply | Two causes, both now gone. The stylesheet was loaded `media="print"` so it would not block the first paint, and the flip to `media="all"` used an inline `onload`, which `script-src-attr` blocks in a built copy — so the fonts silently never applied. Then, even once that was fixed, they only applied when the machine had a connection: offline the stack fell through to Segoe UI, Cascadia Mono and Bahnschrift Condensed, so the tool looked different in the field than on a desk. The four families are now carried in the build (`src/fonts.css`, `src/assets/fonts/`) and the policy names no font host at all. If this recurs, `npm run check:fonts` reports a face whose file is missing and `npm run check:fonts:runtime` measures, inside the shipped WebView2, which family is actually in use. |
| **"Engine: OFFLINE" for the first several seconds** | The frozen sidecar takes 7-23 seconds to start — PyInstaller unpacks and imports scapy, numpy and sklearn | Expected, and load-dependent. Nothing says "starting" yet, which is a known rough edge rather than a fault. If it is still OFFLINE after a minute, open the engine log from Settings. |
| **Capture / STRIKE greyed out** | The Hardware Readiness panel found a missing prerequisite | Settings names what is missing per feature. Usually: not running as Administrator, or an adapter that cannot enter monitor mode. |
| **Capture runs but finds no EAPOL** | Almost always managed mode — most built-in adapters cannot capture 802.11 frames | **Do not read this as "the target is secure."** Confirm with a monitor-mode-capable USB adapter before drawing any conclusion. |
| **CVE data is N days old warning** | Snapshot updates are operator-initiated by design (see [CVE coverage](ENGINEERING_LOG.md#known-gaps-stated-plainly)) | Update in Settings while you have a connection. Findings remain valid for issues known as of that date, and the report states the date. |
| **A MAC in the report ends with a colon** | Up to v1.0.0 every BSSID was stored with a trailing separator — PyWiFi returns one on Windows and `wifi.py` normalised only the bare twelve-character form | Fixed: addresses now go through `netsh_wlan.normalize_bssid`. Rows captured before the fix keep the old value in the database; re-scan to refresh them. |
| **A report page is cut off at the right edge** | A table wider than the printable area | Should not happen now — `npm run check:margins` measures a built PDF against each page box and the WiFi telemetry annexe is landscape. If it returns, that check names the page and the offending width. |
| **Access points are grouped into one numbered circle instead of individual dots** | A stationary survey. Nothing could be located, so they are grouped by where they were heard from | **This is the intended display, not a fault.** From one spot every estimate lands on the receiver — measured at 1.6 m apart across twelve transmitters 30 to 300 m away — so individual dots would stack into an unreadable pile that still implies that many positions. The number on the circle is how many were heard there. Drive or walk past them and they resolve into real positions. See [§4d](AP_LOCATION_METHODS.md). |
| **The vehicle marker moves while you are standing still** | GPS scatter recorded as travel | Fixed in v1.0.0. A fix is only appended to the track once it is `GPS_STEP_M` (5 m) from the last one, so stationary scatter no longer becomes a route. It mattered beyond the display: the track **is** the baseline the localizer trilaterates from, so the scatter was being offered to it as survey geometry. |
| **The vehicle starts somewhere you have never been** | The ego marker was created at `MAP_DEFAULT_CENTER` — central Bangkok — and left visible before any fix arrived | Fixed in v1.0.0: the marker is hidden until a fix exists, so "we do not know yet" is drawn as nothing at all rather than as a position. |
| **Access points wander around the map and never settle** | Up to v1.0.0 the estimators ran even when the receiver had no baseline | Solving for a transmitter a hundred metres away from a cluster of sightings ten metres across is ill-conditioned: a few dB of fading moves the answer by tens of metres. Choosing Multilateration made it *worse*, because the most geometry-hungry method degrades furthest when there is no geometry. `estimateLocation` now refuses before any estimator runs. |
| **GPS shows a heading or a position while parked** | Up to v1.0.0 neither NMEA sentence's own validity field was read | GGA carries `gps_qual` (0 = no fix) and RMC carries `status` ('V' = void); both still contain a latitude and a course, and a receiver that loses lock keeps emitting them, overwriting the last good fix each time. Both are checked now. |
| **Where are the logs / captures / my data?** | Fixed per-user locations, none of them under the install directory | Windows: `%LOCALAPPDATA%\LOCKON-EWAC\` holds `logs`, `evidence`, `data` (the CVE snapshot) and `wordlists` (ones you uploaded); the survey database and credential vault are `%APPDATA%\com.lockon.ewac\ewac.db`. Load the log from Settings without leaving the app. **An uninstall leaves all of it** and now says so. |

## Development

| Symptom | Cause | Solution |
|---|---|---|
| **Python changes not taking effect** | Tauri runs a compiled `.exe` sidecar, not source files directly | Rebuild the sidecar with PyInstaller (see [Install](INSTALL.md#2-build-the-python-sidecar)) |
| **Engine dies instantly with a stderr traceback** | A missing Python dependency (scapy / pywifi / pyserial) — `engine/ipc/handler.py` imports them at module level, before any IPC event can be emitted | `pip install -r engine/requirements.txt` in the venv you build the sidecar from |
| **Engine will not start on an installed copy, `AttributeError: module 'yaml' has no attribute 'error'`** | An orphaned file left in the engine's directory by a previous build | `tauri build` copies the sidecar into `target/release/_internal` **without clearing it**, and Inno had no `[InstallDelete]`, so a file from an older sidecar survived into both. A leftover `_internal\yaml\` holding only PyInstaller's optional C accelerator and no `__init__.py` is read by Python as a *namespace package*, so paramiko's guarded `import yaml` succeeds and returns an empty module — the `except ImportError` never fires. Fixed in v1.0.0 three ways: the installer sources the engine from `src-tauri/binaries/`, it clears `{app}\_internal` before writing, and `npm run check:sidecar` compares the trees and starts the frozen engine. |
| **`link.exe` fails with `0xc0000142` during `tauri build`** | Out of memory, not a code fault | STATUS_DLL_INIT_FAILED means the linker could not initialise. It needs well over a gigabyte to itself, and `CARGO_BUILD_JOBS=1` does not help because the link is one large single process. Close other applications and check for a leftover `rustc.exe` from a cancelled build — one has been seen holding 1.4 GB. The compile has already succeeded by this point, so nothing is lost by re-running it. |
| **Decryptor button disabled** | hashcat is not installed | Install hashcat; the page lists every path it searched |
| **Sidecar fails to start** | Antivirus flagging the PyInstaller binary | Add `src-tauri/binaries/` to your AV whitelist |
| **GPS not reading data** | Wrong COM port or baud rate | Check Device Manager for the correct COM port. Default baud rate is `9600` |
| **No map markers or blue trail in Reports** | Scan was performed without a GPS lock | Ensure the GPS indicator shows "FIX" before scanning. APs without coordinates cannot be mapped. |
| **"No wordlists available" during Dev** | Tauri runs the engine from `target/debug/`, detaching it from the `wordlists/` folder. | `wordlists_path.wordlist_dirs()` resolves it from `sys.executable` (with `sys._MEIPASS` as a fallback) and also reads the per-user upload directory. Go through that module rather than adding a fourth way to guess. |
| **Uploaded wordlist does not appear / upload fails** | Up to v0.1.0 uploads were written beside the sidecar, which is under `%ProgramFiles%` on an installed copy and not writable without elevation | Fixed in v1.0.0: uploads go to `%LOCALAPPDATA%\LOCKON-EWAC\wordlists` and the list shows `BUNDLED` against the ones that ship. Bundled lists cannot be deleted and the button says so rather than failing. |

## System requirements
- **No Administrator privileges required for scanning** - passive and active scanning uses standard user-level APIs (`arp`, `ipconfig`, TCP connect scans).
- **Npcap required for STRIKE & CAPTURE** - To use the STRIKE module for sending Deauth packets or the CAPTURE module for intercepting WPA Handshakes, Npcap must be installed with "Raw 802.11 Packet Capture" enabled. A Monitor-Mode capable Wi-Fi adapter (e.g. Alfa AWUS036ACH, Panda PAU09) is highly recommended.
- **Building needs real disk space** - a full `npm run tauri build` plus the PyInstaller sidecar wants roughly **15 GB** free. Running out shows up as `os error 112` from `rustc`, or as an unexplained failure in the WiX linker (`light.exe`) during MSI bundling, neither of which names the disk. `src-tauri/target/debug` alone reaches 13 GB and is safe to delete — it only costs a slow next `tauri dev`.
- **Windows 10/11 recommended** - Linux support is experimental (some `ipconfig`-specific parsing may need adaptation).
- **Firewall considerations** - Windows Defender Firewall may prompt for network access on first run. Allow both private and public networks for full functionality.
